MCF3M builder onboarding: prerequisite implementation plan

Execute this plan before further work on math-content-builder-revision-plan. Its purpose is to make verified course inputs, instructional rules and review state available throughout the existing builder. Preserve the current pilot, review interface, selected resources and teacher edits.

The revision plan defines the intended destination: a lesson director, one student copywriter, practice design with fading support, purposeful hooks, reusable interactions and formative feedback, coordinated student/reviewer views, independent verification, and durable teacher corrections. This onboarding establishes the shared records those responsibilities will consume.

The repository remains authoritative for what is implemented. Inspect actual files before selecting paths, storage adapters or migrations. Do not describe planned capabilities as completed.

1. Establish the baseline and integration boundary

Owner: parent Cursor agent. Do this first.

Read applicable repository instructions, the current builder entry points, active agent instructions, schemas, lesson records, resource registry, review state and generation commands. Read the input package's README, source register and reconciliation report alongside the full revision plan.

Record the current pilot's content revision, selected resources, locks, approval state and generated output. Identify concurrent user changes and preserve them. Use the repository's existing branch or worktree conventions for isolation.

Produce a short integration map with one row per concern:

ConcernIdentify in the current repository
Lesson identityInternal IDs, course/module/lesson keys and any Drive references
CurriculumExisting codes, exact text, mapping records and coverage claims
RulesActive instruction files, agent prompts, exemplars and precedence
ReviewApprovals, teacher edits, section locks and candidate selections
GenerationInputs read by each stage and how rebuilds are triggered
ResourcesExisting approved entries and their evidence

Classify each required capability as present, partial or absent, citing actual files. Choose the smallest compatible extension. Do not introduce a second builder, parallel manifest system or new runtime service.

Completion condition: the integration owner knows where every imported field belongs and how to preserve existing work.

2. Define one versioned onboarding contract

Owner: integration engineer, coordinated by the parent. Complete before parallel implementation.

Adapt the following entities to the existing schema. These are logical records, not prescribed database tables or filenames.

EntityRequired information
Import batchPackage version/hash, import time, source snapshot date, change summary and outcome
Course/moduleCourse code, module order, instructional title, actual Drive folder title and ID
Lesson identityExisting internal ID, stable course/module/lesson key, Drive ID, parent ID, source title and optional display title
Curriculum sourceCourse, edition, expectation type/code, exact text, sample problem, source locator and text hash
Curriculum mappingLesson/section, expectation reference, rationale, partial-coverage note, origin and review status
Instructional ruleStable ID, scope, requirement, authority/source, version, enforcement owner and supersession relationship
Lesson revisionContent revision, source/rule dependencies, teacher overrides, locks and review state
ConflictAffected record/field, existing value, incoming value, source evidence and resolution status

Keep exact curriculum wording immutable within a source revision. Corrections create a new source revision. Student-friendly goals are separately authored text.

A verified source and an approved mapping are different states. Use independent status fields for source verification, mapping review, content approval and validation results. Passing a validator cannot approve a lesson.

Keep student_content, teacher_notes and provenance structurally distinct. If the current schema differs, provide an adapter and an explicit student-field allowlist. Do not rewrite existing student copy during this migration.

Completion condition: existing records can be represented without information loss, and future revision-plan agents have a shared contract.

3. Implement a repeatable import with field-level reconciliation

Owner: import engineer.

Validate the package first. Import these verified inputs:

  • 39 lesson folder identities across eight modules.
  • 53 specific expectations, nine overall expectations and seven mathematical process expectations.
  • Original lesson titles, current Drive titles, source references and the three recorded title differences.
  • Proposed curriculum mappings with their partial-coverage notes.
  • Instructional rules with explicit provenance and scope.

Resolve identity in this order:

  1. Match an existing exact Drive folder ID.
  2. If there is no Drive match, find a unique existing course/module/lesson identity and attach the observed Drive reference.
  3. If neither exists, create a builder record for the verified lesson.
  4. If matches disagree or more than one record qualifies, record a conflict and continue with unrelated records. Do not guess from a similar title.

Apply these merge rules:

Incoming informationMerge behaviour
Verified Drive title or parentUpdate source metadata; preserve a teacher-authored display title separately
Exact expectation textAdd a versioned source record; flag disagreement with existing purported source text
Proposed mappingAdd a proposal; preserve existing teacher-approved mappings and show differences
Recovered ruleReconcile against current explicit instructions; do not overwrite newer corrections with older plans
Empty approved-resource listPreserve existing resources; empty means this package supplies none
Historical status or exampleRetain only as historical evidence, never as fresh operational state
Teacher edit or locked sectionPreserve content and lock; surface any dependency conflict

Preserve Module 1's actual Module 1 - temp / Async Lessons hierarchy. Use the original JSON for Module 7 order. Supersede the old 32-lesson inventory with 39. Keep asynchronous lesson IDs separate from live-class IDs.

Support a preview of changes and an atomic application using existing storage conventions. Detect changes made after the preview before writing. Rollback must restore only this import's changes and must not erase subsequent teacher work.

Completion condition: a second import of the same package makes no duplicate records, no content changes and no new conflicts.

4. Connect onboarding to the current review interface

Owner: review-interface engineer. Use existing components and styling.

Add a compact import result and course-readiness view. This is the minimum interface needed to inspect onboarding, not the broader visual redesign.

Show:

  • Imported, matched, unchanged and conflicted records.
  • All 39 lessons, grouped in the established module order.
  • Current Drive identity and any source/display-title difference.
  • Proposed versus approved curriculum mappings.
  • Applicable rule version and unresolved conflicts.
  • Existing content, resource and review status without resetting them.

Selecting a conflict should expose the precise difference and supporting source, with a resolution action in the existing review workflow. Apply explicit precedence rules automatically where the evidence is sufficient. Ask the teacher only about genuine unresolved choices.

Do not label a course “covered” because every expectation has a lesson reference. Distinguish mapped expectations from those supported by an actual task and those with reviewed evidence of coverage. Process expectations apply across the course and should remain available without manufacturing a completed coverage checklist.

Explicitly surface the package's known concerns: the partial B1.6 comparison in M1L2, B3.4's TVM requirements, and actual data-collection/application tasks under B2 and C3.

Completion condition: the teacher can understand what was imported and what remains unresolved without reading raw JSON.

5. Give the revision-plan agents the same grounded lesson context

Owner: context-contract engineer.

Create one context resolver using the normalized records. At generation time, resolve the selected lesson's identity, exact expectations, mapping status, applicable rules, current content revision, teacher locks, selected resources and unresolved concerns.

Pass each role only the information needed for its responsibility:

Revision-plan roleOnboarding information it consumes
Lesson directorLesson position, exact expectations, mapping rationale, prerequisites to verify and coverage concerns
Student copywriterAgreed brief, language/flow rules, approved voice examples and protected wording
Practice designerIntended processes, current candidate pool, reinforcement rules and coverage needs
Hook curatorLesson purpose, student-accessibility requirements and resource constraints
Interaction/feedback designersIntended relationship, representations, task requirements and checking constraints
Visual designer/engineersContent boundaries, accessible three-tab contract and display requirements
Independent verifierSource text, applicable rule versions, selected evidence and the rendered lesson

Bind generation to a specific resolved context revision so agents cannot silently work against different rule or source versions. Record references and hashes with outputs rather than duplicating the entire course package in every prompt.

Encode scope explicitly. Three asynchronous tabs are required; the seven-slide live-class sequence applies only to live decks. The historical twelve-candidate pilot does not impose twelve questions on every lesson. Model-STAR plus diagram applies when generating word-problem solutions. A platform named in a plan is not an approved resource.

Completion condition: all future stages receive consistent, traceable context without exposing internal metadata in student directions.

6. Establish targeted change tracking before changing lessons

Owner: integration engineer.

Record which source, mapping and rule versions contributed to each generated section. A new rule or corrected expectation should identify affected sections for review, not trigger an automatic course-wide rewrite.

Classify changes by effect:

  • A folder-title update changes identity/display metadata unless the title is embedded in lesson content.
  • A mapping change affects the relevant brief and coverage review.
  • A student-language rule change affects generated prose and its review.
  • A feedback-rule change affects applicable interaction specifications and checks.
  • A live-slide rule change does not invalidate asynchronous lessons.

Preserve approved outputs as historical revisions. Mark affected current sections as needing review, with a reason. Keep locked text intact and surface the conflict. Rebuild only when the existing workflow requests it.

The existing pilot is the first audit target after onboarding. Save its baseline now; substantive language, practice, hook, feedback and design revisions resume under the revision plan after this prerequisite is complete.

Completion condition: the system can explain what a change affects and preserve teacher control over regeneration.

7. Verify the integration and hand back to the revision plan

Owner: independent verifier.

Check the risks introduced by this integration:

  1. All 39 identities reconcile, with eight module counts of 7, 6, 5, 5, 5, 3, 3 and 5. Re-import is a no-op.
  2. Exact curriculum text survives the adapter unchanged, with valid cross-references and separate sample problems.
  3. Teacher edits, locks, approved mappings and existing resources survive both import and replay.
  4. Ambiguous identity and concurrent-edit fixtures produce conflicts without overwriting records.
  5. Internal metadata cannot appear through the student renderer. Existing student content remains intact.
  6. A changed rule identifies only its relevant dependencies; a live-slide-only rule leaves asynchronous sections unaffected.
  7. The builder can resolve and preview the current pilot using local imported inputs. Student HTML gains no required Drive, model or network dependency.

Produce one integration report with counts, actual changed paths, migration results, unresolved conflicts and verification evidence. Document the commands needed to repeat the import and the rollback boundary.

Onboarding is complete when verified inputs are connected to the builder, source and approval states remain distinct, repeat imports are safe, and the current pilot still works. An unresolved pedagogical mapping can remain visible for review; it must not be silently approved. Block only generation that depends on an unresolved identity or contradictory required input.

Then resume the revision plan at its failure-audit and lesson-brief stages using the imported context. The next substantive output is an improved pilot, followed by the planned check on a substantially different lesson.

Execution order and agent coordination

The parent owns the baseline, shared contract and integration decisions. After the contract is stable, bounded parallel work may cover the importer, context resolver and minimum review interface. Give each engineer distinct file ownership or isolated worktrees, following repository conventions. One integration owner handles shared-schema changes. The verifier reviews the combined result independently.

Finish onboarding before starting further prose rewrites, new interactives, practice expansion, visual redesign, model comparison or batch generation. Preserve their intended requirements in the contract now so those later revisions build on the same evidence and identities.

Boundaries

This plan authorizes no Drive reorganization, new resource approval, public publishing or deployment. Keep school-LMS attendance, grades, participation, session codes and operational data outside the import. Use existing builder storage rather than prescribing changes to school-LMS storage.

No standalone prerequisite learner survey or new onboarding wizard is required. “Onboarding” here means bringing verified course inputs and instructional constraints into the existing authoring workflow.
