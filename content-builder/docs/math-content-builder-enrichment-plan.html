1. Immediate decision

The first dependency is not more content. The review page edits instruction.json, while the renderer compiles student-content.json. A teacher can save edits successfully and rebuild without changing the lesson. Repair this canonical authoring path before expanding the interface or candidate pool.

The active implementation is on content-builder at commit 16e6db249e4917e07181ebf2fd589eb7d5cf5ebb. The pilot is MCF3M Module 4, Lesson 1: The Vertex Form of a Quadratic Function. It is not Module 1. Preserve its approved lesson scope: A2.7 and the vertex-form portion of A2.10. Richness must come from deeper reasoning, not from silently teaching completing the square, the quadratic formula, discriminant, regression, or the full applications lesson early.

Canonical content repair

  1. Retire the review page's write path to instruction.json.
  2. Expose editable, stable blocks from student-content.json.
  3. Save a revision patch against a base version; validate it; rebuild only affected blocks; refresh the same renderer used for export.
  4. Add a save → build → preview integration test. The preview must display the exact saved change.

Several have null answers because “do not invent a source key” has been treated as “do not solve the problem.” Separate those concepts: never fabricate an official key, but do derive an authored solution and independently verify it.

Bloom's revised taxonomy classifies the work a student performs; it is not a verb lookup and not a difficulty scale. “Explain” may still be Understand. Routine equation creation may still be Apply. Connect / Justify / Transfer remain separate portfolio metadata.

Efficient expansion recipes

  • Representation bridge: map corresponding features across forms or graph/equation.
  • Error diagnosis: locate the first invalid step, explain it, repair it.
  • Method choice: select between valid approaches using a stated criterion.
  • Claim testing: prove, qualify or refute a claim.
  • Constraint construction: create a quadratic meeting several conditions and address uniqueness.
  • Model critique: interpret assumptions, meaningful domain and limits.

Pilot target: 24–36 accepted candidates from a baseline of 12, while reporting distinct families separately from numeric variants. A proposed default is that at least 40% of newly accepted families require Analyze/Evaluate/Create when the approved objectives support them. Record exceptions; do not manufacture higher-order padding. The assembled lesson does not need to use every candidate.

Resource-efficient pipeline

  1. Render and segment a source once; cache by source hash + page + region + extraction version.
  2. Run schema, equation, domain, unit, link and duplicate checks before model review.
  3. Retrieve only the relevant source regions, terminology profile and lesson brief for a job.
  4. Generate small batches against ranked coverage gaps; stop when the accepted-family target is met.
  5. Track cost per accepted distinct family, rejection rate and teacher correction burden.

4. Mathematical language becomes governed data

Add a versioned Canadian-English terminology registry with precedence: explicit teacher decision → verified course convention → Ontario curriculum wording → approved topic lexicon. For MCF3M A2.7–A2.11, use standard form, vertex form and factored form. “The writing” is not a substitute for “form.”

WeakRequired direction
The equation is y = … Look at the writing.Consider y = …. Which form makes the vertex easiest to identify?
Starting from y = …, do the vertex.Rewrite y = … in vertex form.
The roots are (1,0) and (5,0).The zeros are 1 and 5, so the x-intercepts are (1,0) and (5,0).
Use the graph below.Name the graph by its stable label and require only actions that object supports.

Use purposeful verbs—consider, compare, determine, sketch, factor, expand, rewrite, estimate, justify, construct, test—without mechanically varying openings. A copy edit must preserve mathematical meaning and cognitive demand.

Remark visibility

  • Essential: remains in the main flow.
  • Optional support: labelled disclosure such as “Term reminder.”
  • Convention note: labelled “Other terminology,” only when a verified conflict is relevant.
  • Teacher/editorial: never enters the student renderer.

Replace “Some books swap those names; this course does not” with direct course terminology. Add a short optional note only if a real source conflict needs explanation. Restore Shawn's exact model-STAR rule: Search, Translate, Answer, Review + supporting diagram; the current rule's Situation/Task/Action/Result definition is incorrect.

5. One compact, accessible card system

The Experience Director owns one component contract shared by interaction, formative-feedback and visual designers. Use cards for bounded learner action, not every paragraph.

ExploreCompass + “Explore”Prompt, representation/tool, observable action.
Worked exampleBook + “Example 1: Comparing methods”Problem, purposeful solution sequence, explanation.
TryPencil + “Try it”Prompt, response, check, hints and retry.
DiscussSpeech bubbles + “Discuss”Shared question and evidence to bring.
CheckCheck-circle + labelDiagnostic task, feedback and next step.
Optional remarkInformation icon + descriptive labelShort collapsed support; never essential content.

Icons reinforce text and never carry meaning alone. Decorative SVGs use aria-hidden. Do not use hover-only or question-mark-only help. A native disclosure or button with accurate aria-expanded is sufficient.

Artifact-aware narrative contract

Every image, graph or tool has a stable object ID, label, capability list, accessibility equivalent and unavailable-state fallback. Copy may reference only declared capabilities. The current pilot violates this twice: it refers to an equation “under” a graph although the live equation is above it, and asks students to mark a highest point on a plain image with no marking interaction.

Every response card defines initial, incomplete, incorrect, partially correct, correct, ungradable and unavailable-tool states. Algebraic checks accept equivalent expressions unless form is the objective. Open explanations use criteria/self-check/teacher review—not unreliable keyword grading.

7. COO-led agent architecture

The COO is a bounded workflow controller, not an autonomous “agent company.” It scopes work, assigns budgets, pins source/rule versions, schedules directors, enforces gates and assembles results. It does not rewrite pedagogy or approve publication.

LayerOwnsTeam
Production COOJob scope, dependencies, budgets, provenance, revision state, release readinessInstantiates only needed directors.
Lesson DirectorPedagogical throughline, prerequisites, sequence, challenge/portfolio connectionsQuestion curator/practice designer, hook curator, student copywriter.
Experience DirectorComponent choice, interaction flow, visual hierarchy, feedback and accessibilityInteraction, feedback, visual and accessibility specialists.
Verification DirectorIndependent rejection/pass reportsMathematical verifier and render/accessibility reviewer as needed.

Extend the nine existing builder specialists; do not recreate them. Directors are responsibility boundaries, not mandatory model calls. One artifact has one writer. Workers return proposed patches against a base revision. The parent/integration writer merges disjoint patches and returns semantic conflicts to the responsible director.

Workflow states

Draft → Grounded → Planned → Producing → Verifying → Review-ready → Approved → Exported. Any state may become Blocked. Publication is a separate explicitly authorized transition.

Operating defaults

  • At most three concurrent specialists per lesson job.
  • One production pass plus one targeted repair pass, then return a blocker.
  • Cache source extraction, curriculum mapping, glossary and component specs by version/hash.
  • A specialist is commissioned only for a bounded artifact with testable acceptance criteria.
  • Use Astra at medium reasoning for the current specialist baseline; make model choice a visible deployment setting.

8. Implementation sequence and gates

  1. Freeze the pilot. Pin branch/hash and keep the current rendered lesson as a before fixture.
  2. Resolve authority conflicts. Restore STAR, three-tab structure and student-content.json as the canonical editable document.
  3. Repair editing. Add stable block IDs, revision/patch/lock contracts and save-build-preview integration.
  4. Ingest Nelson safely. Add the source map, math-region verification, rights status and source-key/authored-solution distinction.
  5. Upgrade pool contracts/index. Bloom + knowledge + family + representation + alignment + verification metadata; FTS filters/ranking; deduplication.
  6. Expand to 24–36 qualified candidates. Generate only against documented coverage gaps; independently solve and review.
  7. Install language and card systems. Terminology registry, contextual lint, object bindings, component registry and shared feedback states.
  8. Replace the review page. In-tool lesson selection, candidate comparison, targeted revisions, diff, autosave and approval.
  9. Add COO orchestration. Bounded jobs, budgets, progress, cancel/resume, dependency-aware rebuild and gate reports.
  10. Scale only after proof. Rebuild M4-L1 and two contrasting lessons; verify edits reach export, cognitive coverage is real, assets/fallbacks work, and generic tests pass before the remaining 39-lesson rollout.

Release gates

  • Every released question has traceable provenance, verified alignment, an answer specification and approval of the current version.
  • Every higher-order classification names the reasoning evidence required.
  • No unverified OCR mathematics, broken object reference, student-visible internal note or inaccessible essential asset.
  • Keyboard, focus, screen-reader, 320 px reflow, 200% zoom, print and unavailable-tool paths pass.
  • Teacher can select another lesson, revise one card, compare, save and approve without touching JSON or leaving the builder.
  • No repository commit, PR, merge, deployment or publication without Shawn's explicit approval.
